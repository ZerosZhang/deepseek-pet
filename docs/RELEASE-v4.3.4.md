# v4.3.4 — 语音与多屏的成体系修复

> **状态**：已发布（2026-10-19）。tag `v4.3.4`；三端构建产物见 Release 附件；main CI 与 tag 构建三端均通过。
> 上一版 v4.3.3 只存活数小时：它把多屏改成了单合成窗，也补上了台词语音与待办播报，
> 但一批**同类缺陷**当时没被一次找全。本版是一次成体系的收口，不是单点补丁。

## 为什么有这个版本

用户原话：「我不想再一直这样出一点小问题修一点了。」v4.3.3 发布后有两位用户报告：

- **#307**（`Hankui3x`）：混合缩放双屏（主屏 1920×1080@100%，副屏 3200×2000@200%）
  下桌宠**完全不可见、不可交互**；「点击台词朗读」开了也不出声。
- 另一位用户：升级到 4.3.3 后**点击台词仍然没声音**，并给出了 `config-slot-0.json`
  里键值变化的证据。

于是做了一次从 4.3.0 到 4.3.3 的**全面盲审**（两个独立模型 + 代码取证），把缺陷按
"模式"而不是"现象"归纳出来。本版修的是这些模式在代码里**已找到的实例**，不只是被
报告的那两个点——审查逐条记在 PR 报告里，未找到实例的模式不当作"已消除"。

## 一、语音：读错了配置层（#307 问题二）

「点击台词朗读」有三个独立断点，任一都足以让它静默失效：

1. **`OverlayShell.cfg` 回的是主配置**。旧架构「一窗一宠」，`win.cfg` 天然是那只宠
   的视图；单合成窗之后它变成单例，`cfg` 退回主配置——而点击朗读判据、台词池、
   角色都读 `host.cfg`。`self_talk_speak_enabled` / `click_show_self_talk` /
   `character` 都是**每宠键**（真值在 `config-slot-N.json`），主配置里根本没有，
   于是判据恒为 False：**气泡照出、就是不朗读、连一行日志都没有**。
2. **音频通道的生命周期判据同样读主配置**（`_self_talk_speak_wanted`），通道可能
   根本没被建起来，或在下一次设置保存时被释放。
3. **`_self_talk_voice_configs` 读了不存在的底层表名**（`_instances`），legacy 拓扑
   下每次取每宠视图都抛 `AttributeError`，被上层 except 吞掉——所以 v4.3.3 的
   legacy 台词语音预缓存其实一直是坏的。

三处都改成读**每只宠此刻真正在用的那份视图**。设置页写进哪个档案，运行期就从哪个
档案读。

## 二、语音：缓存键不是「实际合成输入」的指纹

v4.3.3 的台词缓存以 `md5(文本)` 命名。后果：

- **换音色 / 改语速 / 换后端后，旧句子永远不会重合成**——试听已经是新声音，
  点击台词还是旧声音，重启也没用；edge 与豆包同句甚至落到同一个 mp3 路径。
- 报时缓存的键取"配置里写的音色"，而音色被 preflight 自动回退时实际合成音色
  已经变了——音频与文件身份不符。

现在缓存键由 `provider.flavor(values)`（实际合成输入）参与，即时合成 / 预合成 /
查找三处共用同一份 resolved attempt。外部脚本产出的经典文本 wav 仍作为**独立兼容
来源**保留，但不再凌驾于当前配置的产物之上。

顺带修掉预缓存的单飞语义：合成期间再次保存台词**不再被丢弃**（当前批结束后按最新
名单补跑），合成期间关掉开关**句间即停**（不再整批跑完）。

## 三、多屏：混合缩放会画到屏幕外（#307 问题一）

一张合成窗只能有一个 `devicePixelRatio`。窗口铺满整个虚拟桌面时，Windows 按「窗口
大部分落在哪块屏」给它定一个 DPR，于是必有一侧按错的倍率渲染——报告者主屏
1920×1080@100% + 副屏 3200×2000@200%（副屏物理面积更大）时窗口 DPR 取到 **2.0**，
主屏的桌宠整只被画到可见区之外：**气泡看得见、身体点不到**（他把副屏调成 100% 就
正常，正好证明是这个原因）。

**现在**：多屏且**任意一块屏的缩放不是 100%**、并且开了「允许桌宠跨屏」时，改成
**每块屏一张合成窗**——每张窗的 DPR 天然正确，不存在"按错倍率画"这回事。

判据从"各屏 DPR 不一致"放宽到"任意屏缩放 ≠ 100%"，是因为 Qt 6.12 在 Windows 上对
**负原点屏**返回的是混合坐标系（本机实测：左侧副屏 1920×1080@125%，Win32 原生
`(-1920,0,1920,1080)`，Qt 报 `(-1920,0,1536,864)`——原点是原生像素、宽高是逻辑像素）。
两块屏缩放**相同但不是 100%**（例如双 4K@150%）时，单窗把这块错坐标当真，屏与屏之间
会凭空多出一段"无显示器空洞"、屏自己的外侧边缘反而没有边界（issue #310）。每屏一窗时
每张窗只落在自己那块屏上，那个错坐标根本不参与运算。缩放全是 100% 的多屏仍是单窗，
零变化。

跨屏拖拽的机制是「拖拽期间**不换窗**」：被拖的那只始终留在它原来那张窗里（坐标系、
弹簧、拖拽域都不动），身体跨到邻屏的那一半由邻窗上一份**只读投影**补上——按物理坐标
换算位置，并跟着弹簧每拍刷新，所以松手前宠也会跟着光标走、不会卡在窗边。松手那一刻
才按最终位置提交归属、摘掉投影。

投影的**尺寸口径**是有意的取舍：按目标屏的**逻辑尺寸**画（= 松手后的观感），所以拖过去
时不会先大 1.5 倍再缩回（4K@150% → 1080p@100% 的用户报的就是这个）。代价是接缝两侧
的**物理**尺寸不同（源屏按它自己的 DPR 画），跨缝那一瞬在缝上会看出一点尺度差——
另一条路（按物理像素对齐）能让缝连续，但松手后会缩一次。选了"松手前后一致"。这样做是因为中途换窗会改写一整组弹簧状态，
而且拖动途中反复换窗正是「先撞墙、再瞬移」的成因。

关闭「允许桌宠跨屏」时不需要多开窗，仍只开一张、退化为启动那块屏的可用区。

> 上一版（v4.3.3）在这里做的是「窗口退化为启动屏」，能看见但不能跨屏；本版是正解。
> 日志不再打「跨屏本次不可用」。

## 四、多屏：拖过去的位置没存下来（v4.3.3 回归）

真实鼠标拖到副屏松手后，位置**不落盘**，重启回到旧屏。

根因是两套身份不同步：每 tick 只更新运行期的 `home_screen`，而持久化比较的是
`screen_name`／待写归属；**真实鼠标拖拽路径从来没有调过 `_remember_sprite_screen`**
（只有首撮落种与 `move_sprite_to_screen` 调它，而后者产品里没有调用点）。于是几何
自存看到"盘上屏名 ≠ 实际所在屏"，按「临时承载」整段跳过——一个几何键都不写。

现在拖拽收尾（钳制之后）按最终实际屏补记归属。拔屏的机械迁移仍走「临时承载」，
不会被误记成用户意图。

## 五、提醒：「命令发了」不等于「东西送到了」

`show_bubble()` 在「有审批提醒占着气泡」时**返回 False**，但待办提醒忽略了返回值
——而它**已经盖了 fired 戳**。结果：到点没气泡、没系统通知、之后也不再补。报时与
节日提醒的气泡是同一种写法。

现在「是否真的展示」成为一条明确契约（overlay 与 legacy 的 `show_bubble` 都返回
布尔），气泡没送出时改道系统通知；两条路都不通时留一条 warning，不静默。**不抢占
审批气泡**。

## 六、其他收口

| 修的东西 | 现象 |
|---|---|
| 每日待办跨午夜 | 23:59 的每日待办，电脑 00:00 恢复、只晚一分钟也不提醒（occurrence 只构造今天/明天，漏了"昨天那次仍在宽限窗内"） |
| 进程级服务的角色身份 | 换角色后灵动岛名称、主动识屏发给模型的宠物名、legacy 托盘勾选仍停在默认角色（都读全局 `character`，而它是每宠键） |
| 点击内容设置的显隐 | 只开「点击自言自语」时，候选台词 / 配图目录 / 配图概率 / 显示时长被隐藏（显隐依赖周期开关，而点击链路早就独立了） |
| 刷新率变更的通知范围 | 副屏从 60Hz 改成 180Hz，tick 仍按旧频率（取数枚举全部屏，但只订阅了窗口自己那块屏） |
| 帧率采集攒满自己的 ETW 会话 | 玩着游戏不出 FPS，日志只有 `error 1450`（系统资源不足）；本机实抓到 11 个 `Running` 旧会话 |

**关于 FPS 那条**：真因不是权限。桌宠每次异常退出（被强杀/崩溃时走不到官方
`--terminate_existing_session`）都会留下一个 `dsh-pet-fps-*` 的 ETW 会话，
Windows 对同时存在的 trace 会话有上限，攒到十几个以后新会话直接报 `1450`。
本机 `logman query -ets` 实抓到 11 个 `Running` 的旧会话。现在每个进程**第一次**
开会话前按前缀列出、排除本次会话名、逐个 `logman stop`（实测**不需要管理员**，
也绝不用通配去抢别人的采集会话），日志会打「帧率采集：清理 N 个残留 ETW 会话」。

只扫一次是有意的：`logman query -ets` 实测 **970 ms** 中位（5 次，本机），
`logman stop` **56 ms**。残留来自**启动前**就已经堆积的那批（上一次强杀/崩溃留下的）；
本进程自己的会话在正常停止路径上都走官方 terminate 收掉，所以启动后扫一次就够，
换游戏目标时重查一遍纯属白付一次系统调用。清理时排除**本进程建过的全部会话名**
（不只当前那个）：`stop(wait=False)` 之后立刻 `start()` 时旧线程可能还卡在那次查询
里，此时新会话已经起来了。查询失败不关闸，下一次开会话会再试一次。

## 六点三、设置页搜索：Ctrl+F 直接搜

设置页本来就有搜索框（打在侧栏，命中就跳页 + 高亮 + 回车翻页），但**只能用鼠标点进去**。
现在在设置窗任意位置按 **Ctrl+F** 就能把光标送进搜索框并全选，接着打字即可。

翻命中现在有三条路：**回车 / ↓ 前进，↑ 后退**（第一条上按 ↑ 回绕到最后一条）。
方向键翻结果比按回车循环更符合直觉（浏览器查找栏、VSCode、Windows 设置搜索都是这样），
单行输入框里 ↑/↓ 本来没有默认行为，不会和光标移动抢键。

顺带补齐了索引：「更新」页那几条作者账号（BiliBili / 抖音 / GitHub）以前搜不到，现在
按平台名或账号名都能搜到。**没有**改成"只显示命中行"的过滤式搜索——跳转式不会把人困在
空列表里。侧栏的「恢复默认设置 / 保存并退出」仍不进搜索（那是命令，不是设置）。

## 六点四、新增：三个动作的全局快捷键（默认不绑）

「AI 对话 / 看看屏幕 / 截图提问」现在可以在 **设置 → 互动 → 快捷键** 里各录一个
**系统级**组合键（在别的程序前台时也生效）。

- **默认全空**：不绑任何键，行为与这一版之前逐位相同；右键菜单照常可用。
- **必须有修饰键**（Ctrl/Alt/Shift/Win）：单个字母的全局热键会抢走系统级打字。
- **被占用不会假装成功**：Windows 的全局热键表是独占的，注册失败（通常是被别的程序占了）
  那一项就不生效，主进程日志里记一条 `全局快捷键未生效：…`。设置页三行的说明里**提前
  写明了这个后果**——设置页是独立进程，拿不到主进程的注册结果，所以它不会去显示一个
  自己无法确认的「已生效」。
- 走的是右键菜单同一条入口，没有第二套实现。
- 只有 Windows 能注册系统级热键；其它平台设置项可见可存但不注册。

## 六点五、交付前双模型审查修掉的（v4.3.4 收尾）

发布前用两个模型各做了一轮只读审查，交叉验证出同一批"按宿主分片"的缺口，本版修掉：

| 问题 | 现象 | 修法 |
|---|---|---|
| 屏拓扑不跟 `_hosts` 同步 | 拔掉副屏后宠留在失效宿主；插屏不建窗，拖不过去 | 新增拆窗流程（成员按比例并回存活宿主 + 关窗 + 断信号 + driver detach），插屏建宿主 |
| 窗口自己监听屏信号并重算整张桌面 | 改分辨率/任务栏/刷新率后副屏窗扩成全桌面，**#307 的显示错误原样复活**（探针 `1536×816 → 4480×1392`） | 窗口几何来源改成"它自己那块屏" |
| 跨窗移交删光位置监听、跟随器缓存旧原点 | 气泡停在旧位置、之后不再跟宠走 | 移交后重绑监听 + `set_origin` |
| 投影用当前位置反算"旧位置" | 旧像素擦不掉（残影） | 保存上次真正绘制的矩形 |
| 副屏右键菜单写主窗控制器 | 副屏选动画/移动没反应 | 按宿主取控制器，`no_move` 对所有宿主同步 |
| 快速聊天锚点用主窗原点 | **启动就在副屏的宠**一开聊天偏一整块屏 | 用 `_sprite_origin(sprite)` |
| 整窗显隐的 clip 恢复只走主窗 | 副屏宠完全静止、连帧都不换 | 取每张窗的成员表 |
| 岛桥永远只绑主宿主 | 岛在副屏时，副屏的宠**能穿过岛**、拖岛拍鱼无效 | 按岛自己所在那块屏绑宿主，岛移动/换屏时重绑 |
| 岛的「是否还有宠可见 / 显示桌宠」漏副屏 | 主窗空着就误判无宠，副屏被藏的宠叫不回来 | 判据与恢复遍历全部宿主 |
| 弹弓每张窗按自己局部坐标画同一会话 | 副屏瞄准时主屏出现**幽灵弹弓**；副屏 Esc 后 grab 还挂着 | 会话记 `owner`：只有 owner 画，Esc 路由到 owner 并连 grab 一起收 |
| 多窗几何变化直接 return | 气泡留旧位置、分辨率变化后比例被硬钳 | 逐 host 完整事务：收拖拽 → 取比例 → 换域 → 落位 → 同步气泡原点 → DPR |
| 显示缩放信号只喂主宿主 | 副屏改缩放时那张窗的精灵不换 DPI | 逐宿主喂 |
| 拔屏后岛墙留在已拆宿主 | 拔屏到岛下次移动之间，宠撞不到岛 | 拔屏时主动重绑一次 |
| 运行中改缩放不重排宿主 | 把副屏从 100% 改成 125% 后，判定翻成「多窗」却没有窗，副屏的宠被按主宿主重排；改回一致时旧宿主又挂着成员 | 缩放信号里统一重排宿主，再按档案里记的屏归属把每只送回自己那块屏 |
| 跨窗后气泡跟随器没重挂 | 气泡停在跨屏前的位置、之后不再跟宠走；主宠那只还偏了一整块屏 | `SpriteBubbleFollower.rebind()` 换窗重注册；主宠经 `_bubble_for` 取（原先取错表 = 整段静默跳过） |
| runtime 标记监听写死主窗 | 主宠拖到副屏后，runtime 标记不再跟目标窗走 | 按 `_host_of` 取它现在所在那张窗 |
| 拔屏后岛墙重绑被多窗判定早退 | 拔掉混合缩放的副屏后只剩一块屏，桥仍引用已拆宿主的世界，宠撞不到岛 | 去掉多窗早退：重绑只看"目标宿主是不是当前绑的那个" |
| 拖拽放宽域按逻辑桌面算 | 右侧高 DPI 屏（1920 物理 @200% 只占 960 逻辑宽）拖到中段就跟不上鼠标 | 按各屏**物理**外接矩形换算到源窗局部 |
| 岛关着但碰撞墙照建 | legacy 拓扑下**拖不动、也不漫游**，日志里一个字都没有 | 岛为 None 时不建碰撞体；墙判据加判空（`island_collision.py` 里那个 `NoneType.isVisible` 已实测复现，行号与报告一致） |
| 跨混合 DPI 拖拽时投影按物理像素画 | 4K@150% 拖到 1080p 目标屏上先大 1.5 倍、松手瞬间缩回（用户报成「拖过去缩放不对」） | 投影按**逻辑尺寸**画 + 开平滑采样 |
| 两块屏缩放相同但都不是 1:1 | issue #310：Qt 给负原点屏报「原生原点 + 逻辑宽高」，单窗把错坐标当真，屏间凭空多出空洞 | 每屏一窗的判据从「DPR 不一致」放宽到「多屏且任意屏 DPR ≠ 1」 |
| 残留会话清理只排除"本次会话名" | `stop(wait=False)` 后立刻 `start()` 时，旧线程还在查询，会把新会话当残留停掉 | 排除本进程建过的**全部**会话名；查询失败不关闸，下次再试 |
| 打包门禁无条件要求 Windows 依赖 | TTS 产物门禁是三端共用的，却无脑要求 Windows-only 的 `win32ctypes`，干净的 Linux/macOS 构建被自己的门禁判红 | 平台专用模块单列，只在该平台目标上要求；补正反向用例 |
| 凭据「能不能用」靠扫类名子串 | 判据是 `"fail" not in name`，于是名叫 `company.failover.Keyring` 的**合法可写**后端被判成「没有钥匙串」 | 只认 keyring 自己的 `fail` / `null` 两个占位类（全名 + 类身份双重判据） |
| 只读文本只能鼠标选中，Ctrl+C 没反应 | 截图翻译、截图问答、聊天窗里选出一段文字按 Ctrl+C 无反应，只能右键菜单复制 | ①窗口不再带 `WindowDoesNotAcceptFocus`（它连「点击后激活」也禁掉），只保留「打开时不激活」；②8 处只读控件补上键盘选中与 `ClickFocus` |

## 七、没有修的（如实）

**issue #286**（Windows 11 + 150% DPI 下桌宠不可见、鼠标整屏失效）**仍未解决**，
本版不含它。报告者在 v4.3.1 上补了三条很有价值的观察：

- overlay 拓扑下 `WS_EX_TRANSPARENT` 常驻，`SetCursorPos` 移到身体中心也不取消 →
  看得见点不到；
- legacy 拓扑下拖不动、右键需「先左键激活」；
- `overlay-active-pets.json` 退出时被写成空、启动时不注册自己（代码注释写明这是
  「启动期不替用户改盘」的有意设计，所以这一条属产品语义争议，不是明确缺陷）。

前两条**需要 150% 缩放的真机环境加现场探针**才能定位。本机只把副屏调到过 125%
（150% 没试过），复现不出他的症状，不做「猜一个改法」的修复。

**跨屏还有两条边界没做**（都需要把对象精确拖到缝上才触发，已知不影响日常使用）：

- **跨窗拖拽期间没有碰撞**：从 A 拖一只到 B、仍按着鼠标时，它能与 B 的宠重叠，松手归窗后才分离。要做得引入跨窗物理代理，留到 4.3.5。
- **岛横跨两屏缝上时只绑一侧**：岛正好压在接缝上（一半主屏一半副屏）时，墙只建在岛所在那块屏的世界里，另一侧的宠会穿过去。只有把岛精确拖到缝上横跨才触发。

**那条 `401`「AI 对话请求失败」没定位到代码缺陷**（用户反馈共三条：`thinking` 参数格式与
「重写 config 清空活跃宠」两条核验为不成立；`401` 这条原先判"真"，**但根因后来被推翻了**，
原文的 `win32ctypes 缺包` 结论作废，现在只能是"现象真、根因未定位"）：

- **本版加的是加固，不是那次的根因修复。** 原先的判断「4.3.3 的冻结包缺 `win32ctypes`，
  钥匙串后端不可用，读到的 Key 是空串」**不成立**。证据分两项，别混看：
  - **旧部署 exe 的清单检查（产物层）**：用 `PyInstaller.archive.readers.CArchiveReader`
    读 `D:\dsh-pet\dsh-pet-standalone-webm-chat.exe` 的 exe 头 TOC → 打开内嵌 PYZ →
    2902 个模块名，其中 `win32ctypes` 27 个、`win32ctypes.pywin32.win32cred` 1 个、
    `win32ctypes.core` 21 个。**旧包有这个依赖。**（`_internal` 目录里看不到它只是
    「纯 Python 模块进 PYZ」的正常表现，不是缺包。）
  - **新产物目录的外部解释器导入（模块层，不是冻结进程）**：以
    `dist-onedir/.../\_internal` 作 `sys.path`、`python -S` 隔离系统 site-packages，
    `import win32ctypes.pywin32.win32cred` 成功。这证明**包内那份 `.py` 能被同版本
    解释器加载**，不等于"在冻结进程里验证过"。
- **截图证据方向相反**：服务端回的是 `401 Authentication Fails, Your api key: ****cdeb
  is invalid` 并带 `request id`——它拿到的是一个**非空的具体 key**（尾号 4 位），不是空串。
  空 Key 的症状不是这条。至于那个 key 为何无效（失效 / 填错 / 服务商不匹配 / 选中了旧
  凭据条目），**没有证据支持任何单一结论**，如实留作未定位。
- 因此本版做的是：Windows 构建期显式收集并门禁 `win32ctypes`（防将来 hook 失配时
  静默丢）、凭据存储不可用/读写失败时**不再静默**（写 warning），并在判定后端时只
  认 `fail`/`null` 两个占位类。**遇到 401，先核对 Key 与 base_url，再重填一次。**
- **复核用的真机证据（本机，探针值）**：用打包机上的 CPython 3.13（与打包同版本）
  跑三个独立进程，后端 `keyring.backends.Windows.WinVaultKeyring`；进程 A
  `keyring.set_password('dsh-pet-standalone','probe-<uuid>', ...)` → 进程 B
  `get_password` 读回一致（`MATCH = True`）→ 进程 C 删除后读回 `None`。这证明**本机
  OS 凭据库 + 该 keyring 后端**跨进程持久正常；**未在冻结 exe 进程内自动验证**（冻结
  exe 没有可注入代码的通用入口），这一条由实机验收覆盖：填一次 Key、重启、确认设置页
  仍显示已保存且日志无「凭据存储不可用」。

**测试跑久了偶尔崩一次（已加防护，但没找到根因）**

开发最后阶段发现：把整套测试放在一个进程里连续跑（约 25 分钟）时，偶尔会触发一次
Windows 原生崩溃。它不影响你日常使用，但会让"完整回归"这个动作本身不可靠。修了一处
跨屏气泡跟随器的定时器收尾顺序之后，连续四次完整回归都没再出现。

**说明清楚**：我没有抓到崩溃时的原生调用栈，也没做"只撤掉那一处"的反向验证，所以
不能说"根因已确认"——准确的说法是"加了这处防护后未再复现"。如果以后又出现，第一步是
去抓栈，而不是再猜一次。

另一条同类说明：设置页搜索的 ↑/↓ 翻命中已经有测试覆盖（含带 Ctrl/Shift 时不翻页），
但**真实输入法在打候选词时的行为没有实机验证过**。

## 八、升级说明

**配置不用动**：没有格式变更、没有键改名，旧配置直接能用。

**如果你有多块屏**：

- 每块屏的缩放**都是 100%**：和以前一样，一张窗铺满整个桌面。
- **有任意一块屏的缩放不是 100%**（比如副屏 125%）：每块屏各有一张窗，跨屏照常拖。
  这是本版唯一的行为变化点——以前这种配置下跨屏会出问题，现在能用了。

**换音色后，第一次播放会重新合成**（缓存按音色区分了），属正常。唯一例外：如果你以前
用脚本在 `cached_audio` 里生成过 `<md5>.mp3` 这类文件，它跟程序自己生成的产物长得一样、
程序分不出来，会被当成旧缓存直接播放。想让新音色立刻生效，把 `cached_audio` 里对应的
`<md5>.*` 删掉即可。
